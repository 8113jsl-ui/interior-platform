제가 이해한 설계안을 **제품의 목적 → 화면 구조 → 역할별 업무 → 기능 구현 방법 → 서버와 권한 → 개발 순서 → 미결정 사항** 순서로 정리하겠습니다.

아래에서 **문서 기준**은 첨부 설계안에 있는 내용이고, **구현 제안**은 이를 실제 서비스로 만들기 위한 제 판단입니다. 문서 자체가 보류한 정책은 확정 사항으로 취급하지 않았습니다.

**1. 이 서비스가 해결하려는 문제**

이 플랫폼의 중심은 ‘인테리어 프로젝트별 정보와 소통의 관리’입니다.

도안은 파일로, 자재는 표로, 고객 요청은 메시지로, 현장 사진은 다른 대화방으로 분산되면 어느 자료가 최신인지, 무엇을 고객에게 공개했는지, 어떤 요청에 답했는지 확인하기 어려워집니다. 이 정보를 **하나의 프로젝트 아래에서 연결하는 것**이 제품의 목적이라고 이해했습니다.

사용자가 프로젝트에 들어왔을 때 다음 질문에 답할 수 있어야 합니다.

- 지금 어떤 공정이 진행 중인가?
- 확인해야 할 도안과 자재는 무엇인가?
- 고객이 요청한 내용과 답변은 무엇인가?
- 최근 현장 상황은 어떤가?
- 다음 일정은 언제인가?
- 현재 확인해야 할 견적 버전은 무엇인가?

PM·고객·시공팀은 서로 다른 서비스를 사용하는 것이 아니라, **같은 프로젝트의 데이터를 서로 다른 범위에서 다룹니다.**

---

**2. 전체 화면 구조와 메뉴 배치**

문서 기준의 구조는 다음과 같습니다.

```text
PM 영역
├─ 프로젝트 목록
│  └─ 프로젝트
│     ├─ 개요
│     ├─ 도안·시안 → 도안 상세
│     ├─ 자재 → 자재 상세
│     ├─ 고객 요청 → 요청 상세
│     ├─ 시공 사진 → 사진 상세
│     ├─ 일정 → 일정 상세
│     ├─ 견적서 → 견적서 상세
│     └─ 프로젝트 설정
├─ 고객 관리 → 고객 상세
├─ 전체 캘린더
├─ 변경이력 → 변경기록 상세
├─ 알림
└─ 업체 설정 [권한 정책 보류]

고객 영역
├─ 내 프로젝트
│  └─ 프로젝트
│     ├─ 프로젝트 홈
│     └─ 공개된 6개 업무 탭 → 항목 상세
└─ 알림

시공팀 영역
├─ 현장 사진
│  ├─ 배정 현장 선택
│  ├─ 사진 업로드 상태
│  └─ 사진 상세
└─ 알림
```

여기서 중요한 설계 원칙은 **업무 데이터의 원래 위치를 하나로 유지하는 것**입니다.

예를 들어 고객 상세에서 관련 프로젝트를 눌렀다면 프로젝트 개요로 이동합니다. 고객 상세 아래에 또 다른 프로젝트 관리 화면을 만들지 않습니다. 전체 캘린더에서 일정을 눌러도 프로젝트 내부의 일정 상세로 이동합니다.

구현 시에는 화면별로 다음 정보를 관리하는 화면 레지스트리를 두는 것이 좋습니다.

| 관리 항목 | 목적 |
|---|---|
| 화면 ID | PM-05, CL-15처럼 설계 문서와 코드 연결 |
| 부모 화면 | 해당 화면의 소속 확인 |
| 뎁스 | 불필요하게 단계가 늘어나는 것 방지 |
| 허용 역할 | 화면 진입 대상 구분 |
| 정규 경로 | 알림·검색·캘린더에서 같은 상세로 연결 |
| 필요한 권한 | 조회·수정·공개·다운로드 구분 |

모달, 필터, 탭 전환, 저장 버튼을 누른 상태까지 별도 페이지로 만들 필요는 없습니다.

**3. PM의 업무 흐름과 구현 방법**

PM의 시작점은 별도 대시보드가 아닌 **프로젝트 목록**입니다.

| 화면 | 문서 기준 | 구현 방법 제안 |
|---|---|---|
| 프로젝트 목록 | 허용 프로젝트, 검색·상태 필터, 간단한 현황 | 프로젝트명·현장 검색, 상태별 필터, 목록과 요약 수치에 동일한 조회 범위 적용 |
| 프로젝트 공통 영역 | 프로젝트명·현장·기간·탭·프로젝트 전환 | 어느 탭에서도 현재 프로젝트를 인지할 수 있는 공통 헤더 사용 |
| 개요 | 현재 공정·최근 업데이트·다음 일정·고객 홈 미리보기 | 각 요약에서 해당 원본 상세로 이동 |
| 프로젝트 설정 | 기본 정보·공개 상태·참여자 관리 위치 | 일반 정보 수정과 권한 부여 기능을 구분 |
| 고객 관리 | 연락처·관련 프로젝트 | 고객 연락처와 로그인 계정을 별도 데이터로 관리 |
| 전체 캘린더 | 허용 프로젝트 일정 통합 | 일정 선택 시 해당 프로젝트 일정 상세로 이동 |
| 변경이력 | 필터·변경 전후 값 | 서버에서 변경자·시간·대상·전후 값을 기록 |

실제 사용 흐름은 다음과 같습니다.

> 프로젝트 생성 → 현장·기간 입력 → 개요 확인 → 도안·자재 등록 → 고객에게 공개할 항목 선택 → 요청 답변 → 사진·일정 업데이트 → 견적 버전 관리

다만 **프로젝트 생성과 동시에 고객 초대나 시공팀 배정을 자동 실행하면 안 됩니다.** 초대·배정 권한은 문서에서 별도 결정 대상으로 남겨 놓았습니다.

고객 홈 편집도 프로젝트의 원본 자료를 복제하는 방식은 피하는 것이 좋습니다. 안내 문구와 표시 순서 등을 조정하되, 일정·자료·최근 업데이트는 같은 원본 데이터를 참조해야 합니다.

**4. 6개 업무 기능의 세부 동작**

**① 도안·시안**

문서 기준은 SKP·PDF·DWG 원본을 관리하고, 별도의 이미지로 비교하는 것입니다.

권장 데이터 구분은 다음과 같습니다.

| 데이터 | 내용 |
|---|---|
| 도안 기록 | 제목, 설명, 프로젝트, 공개 상태 |
| 원본 파일 | 파일명, 실제 형식, 용량, 저장 위치 |
| 비교 이미지 | 이미지 파일, 식별명, 연결된 도안, 필요시 PDF 페이지 |
| 작업 기록 | 등록자·등록 시각·변경 내용 |

업로드는 다음 순서로 처리하는 것이 좋습니다.

1. 브라우저에서 허용 확장자와 용량을 먼저 검사합니다.
2. 서버에서 업로드 권한과 실제 파일 형식을 다시 검사합니다.
3. 검증을 마친 파일만 정상 자료로 등록합니다.
4. 미리보기 또는 비교 이미지를 원본과 연결합니다.
5. 공개 설정을 적용하고 변경기록을 남깁니다.

확장자를 `.pdf`로 바꿨다는 이유만으로 PDF라고 신뢰해서는 안 됩니다. 브라우저 검사는 사용자의 실수를 줄이는 용도이며, 실제 저장 허용 여부는 서버가 판단해야 합니다.

A/B 비교는 다음 조건을 만족해야 합니다.

- 같은 프로젝트의 이미지 두 장을 선택합니다.
- A는 왼쪽, B는 오른쪽에 둡니다.
- 두 이미지는 같은 표시 영역에 겹칩니다.
- 핸들을 움직이면 A의 노출 범위만 바뀝니다.
- 0%는 B만, 100%는 A만 표시합니다.
- 이미지 비율을 유지하며 강제로 늘리지 않습니다.
- 키보드 방향키와 터치를 지원합니다.
- 이미지 부족·읽기 실패·접근권한 부족 상태를 구분합니다.

고객이 비교할 때는 **A와 B 모두 접근 가능한 이미지인지** 검사해야 합니다. 한쪽만 공개된 상태에서 비공개 이미지를 비교에 사용하는 일이 없어야 합니다.

도안의 이전 버전 보존 정책은 미결정이므로, 새 파일을 올렸다는 이유로 기존 파일을 자동 삭제하는 방식은 피해야 합니다.

**② 자재**

자재는 구매 시스템이 아니라 **프로젝트에서 사용할 자재의 사양과 결정 상태를 공유하는 기능**으로 이해했습니다.

기본 항목은 카테고리, 적용 공간, 이미지, 사양, 수량, 단가, 확정 상태입니다. 목록에서는 카테고리와 공간을 기준으로 찾고, 상세에서는 적용 위치와 결정 기록까지 확인합니다.

구현 시에는 다음을 구분해야 합니다.

- 자재 정보의 수정
- 고객에게 보이는지 여부
- 자재가 확정됐는지 여부
- 누가 어떤 내용을 확정했는지 기록

‘공개’와 ‘확정’은 다른 상태입니다. 공개했다고 확정된 것이 아니고, PM이 내용을 수정했다고 고객이 동의한 것도 아닙니다.

**확정 후 주요 사양이 변경됐을 때 재확인을 요구할지**도 운영 전에 결정해야 합니다. 문서에서 고객 확정자 지정 방식이 보류되어 있으므로 현재 단계에서 임의로 확정 버튼을 활성화하면 안 됩니다.

**③ 고객 요청**

핵심은 **요청 원문을 보존하는 것**입니다.

고객이 내용을 바로 덮어쓰는 방식보다는 다음 구조가 적합합니다.

```text
최초 요청 원문
├─ 고객 정정 기록 1
├─ 고객 정정 기록 2
├─ 담당자 답변
└─ 상태 변경 기록
```

문서상 흐름은 요청 등록 → 담당자 확인·답변 → 처리 상태 변경입니다.

구현 제안은 원문·정정·답변·상태 변경을 별도 기록으로 남기는 것입니다. 그래야 나중에 “처음에는 무엇을 요청했고, 언제 무엇이 달라졌는가”를 확인할 수 있습니다.

다만 담당자 배정 규칙, 처리 기한, 완료 후 재요청 방식은 문서만으로 확정할 수 없습니다.

**④ 시공 사진**

사진은 공정, 촬영일, 설명, 업로더, 등록 시각, 공개 상태를 관리합니다.

여기서 **촬영일과 업로드 시각은 다릅니다.** 어제 촬영한 사진을 오늘 올릴 수 있으므로 둘 다 저장해야 합니다.

다중 업로드 시에는 파일별 성공·실패를 구분하는 방식을 권장합니다. 일부 파일이 실패해도 어떤 사진이 저장됐는지 확인할 수 있어야 하며, 재시도 시 중복 등록을 방지하는 처리가 필요합니다.

시공팀 업로드에서는 사용자가 입력한 이름을 업로더로 신뢰하지 않고, 로그인 계정에서 업로더를 결정해야 합니다. 사진 업로드는 현장 기록이며 공사 완료 처리와 연결하지 않습니다.

**⑤ 일정**

일정은 같은 데이터를 두 방식으로 보여줍니다.

- 월간 달력: 특정 날짜에 무엇이 있는지 확인
- 프로젝트 타임라인: 전체 기간의 흐름 확인

전체 캘린더는 여러 프로젝트의 일정을 모아 보는 화면이고, 실제 편집 위치는 해당 프로젝트의 일정 상세입니다.

운영 데이터에는 날짜뿐 아니라 시작·종료 시각과 시간대 처리도 고려하는 것이 좋습니다. 다만 반복 일정, 외부 캘린더 연동, 자동 공정 계산은 현재 문서의 확정 범위로 보지 않았습니다.

**⑥ 견적서**

견적은 PDF 파일 하나를 덮어쓰는 구조보다 **견적 묶음과 버전 기록을 분리하는 구조**가 적합합니다.

```text
견적 묶음
├─ 버전 1: PDF / 변경 설명 / 공개 상태
├─ 버전 2: PDF / 변경 설명 / 공개 상태
└─ 버전 3: PDF / 변경 설명 / 공개 상태
```

각 버전에 등록 시각, 작성자, 변경 설명, 공개 시각을 기록합니다.

고객은 허용된 공개 버전만 봐야 합니다. 최신 비공개 버전이 있다는 이유로 고객 화면에 그 파일명이나 변경 설명이 노출되어서도 안 됩니다.

새 버전 공개 시 이전 버전도 계속 보여줄지, 현재 유효한 버전을 별도로 표시할지는 추가 정책으로 정하는 것이 좋습니다.

---

**5. 고객과 시공팀의 구체적인 이용 방법**

고객은 초대된 프로젝트를 선택한 뒤 프로젝트 홈에서 진행 상황을 확인합니다.

> 내 프로젝트 → 프로젝트 홈 → 공개 도안·자재 확인 → 요청 작성 또는 정정 → 담당자 답변 확인 → 일정·사진·견적 확인

프로젝트 공개 여부만으로 아무 고객이나 접근할 수 있어서는 안 됩니다. **초대 또는 배정된 프로젝트인가**를 먼저 검사한 뒤, 그 안에서 공개된 자료를 보여줘야 합니다.

고객 확정 기능은 단순한 역할 구분보다 세밀합니다. 같은 프로젝트에 고객 계정이 여러 개 있어도 최종 의사결정자는 일부일 수 있으므로, 일반 조회 고객과 확정 권한자를 구분할 수 있어야 합니다. 다만 지정·회수 방식은 미결정입니다.

시공팀은 다음처럼 단순해야 합니다.

> 현장 사진 진입 → 배정 현장 확인 → 사진 선택 → 공정·촬영일·설명 입력 → 업로드 → 같은 현장의 목록 갱신

배정 현장이 하나면 자동 선택하고 여러 개면 선택을 요구합니다. 선택하지 않았거나 배정 기간이 끝났으면 업로드를 허용하지 않습니다.

업로드 도중 배정이 회수되는 경우도 있으므로, 화면 진입 시 검사뿐 아니라 **최종 등록 시점에도 서버에서 다시 확인**해야 합니다.

---

**6. 권한은 ‘역할 하나’로 결정하면 안 됩니다.**

이 서비스의 접근 판단은 다음 조건의 조합입니다.

```text
로그인 계정
+ 활성 업체 소속
+ 해당 프로젝트의 배정
+ 역할별 허용 행동
+ 배정 유효 기간
+ 항목의 공개 상태
+ 필요한 개별 권한
```

예를 들어 고객이 자재 상세를 요청했다면 서버는 다음 순서로 확인해야 합니다.

1. 로그인된 계정인가?
2. 요청한 프로젝트에 유효하게 배정되어 있는가?
3. 해당 자재가 실제로 그 프로젝트에 속하는가?
4. 프로젝트와 자재가 고객에게 공개되어 있는가?
5. 요청한 행동이 조회인가, 수정인가, 확정인가?
6. 그 행동을 수행할 권한이 있는가?

화면의 버튼을 숨기는 것은 사용성 처리입니다. 실제 거절은 API와 데이터베이스에서 이루어져야 합니다.

알림·검색·파일 다운로드·이미지 비교에도 같은 원칙이 적용됩니다. 이미 받은 링크라도 권한이 회수되면 이후 접근이 제한되어야 합니다.

또한 화면에는 ‘해당 항목에 접근할 수 없음’ 정도로 안내하고, 권한이 없는 프로젝트명이나 파일명을 오류 메시지로 노출하지 않는 편이 좋습니다.

---

**7. 서버와 데이터는 어떻게 구성할 것인가**

앞서 제안한 Supabase 기반 구성을 전제로 하면, 실제 개발에서는 데이터를 다음 단위로 나누는 것이 적합합니다. 이는 **구현 제안**입니다.

| 영역 | 필요한 데이터 |
|---|---|
| 계정·업체 | 사용자, 업체, 업체 소속 |
| 프로젝트 접근 | 프로젝트, 참여자 배정, 역할, 유효 기간 |
| 고객 연락처 | 고객 연락처, 관련 프로젝트, 필요시 계정 연결 |
| 도안 | 도안 원본, 비교 이미지 |
| 자재 | 자재 정보, 이미지, 추후 확정 기록 |
| 요청 | 원문, 정정, 답변, 상태 변경 |
| 사진 | 파일, 공정, 촬영일, 업로더 |
| 일정 | 시작·종료 시각, 내용, 관련 항목 |
| 견적 | 견적 묶음, 버전별 파일 |
| 공통 | 파일 메타데이터, 변경이력, 알림 |

현재 검토판처럼 모든 것을 하나의 브라우저 저장 객체에 넣는 구조는 운영용으로 유지하지 않습니다.

저장 처리의 권장 방식은 다음과 같습니다.

> 입력 검증 → 서버 권한 검사 → 데이터 변경 → 변경이력 기록 → 성공 응답 → 화면 갱신

데이터 변경과 변경이력 생성은 가능하면 같은 트랜잭션으로 처리해야 합니다. 자료는 바뀌었는데 이력이 남지 않는 상황을 막기 위해서입니다.

동시 수정도 고려해야 합니다. 두 PM이 같은 항목을 열고 수정했을 때 나중 저장이 앞선 수정을 조용히 지우지 않도록, 버전 번호나 수정 시각을 비교하고 충돌을 안내하는 방식을 권장합니다.

파일은 비공개 저장소에 두고 데이터베이스에는 파일의 식별자와 메타데이터를 저장합니다. 브라우저에 운영 비밀 키를 넣거나 모든 파일에 영구 공개 URL을 부여하는 방식은 사용하지 않습니다.

---

**8. 디자인은 어떻게 적용할 것인가**

Heron에서 유지할 부분은 다음과 같습니다.

- 종이 같은 배경 질감
- 가는 선과 격자
- 직각 프레임
- 큰 제목과 조밀한 정보의 대비
- 주황색 강조
- 도면 같은 선형 그래픽
- 좌표 커서와 절제된 등장 모션

하지만 업무 화면에서는 마케팅 페이지와 목적이 다릅니다. 사용자는 매번 긴 연출을 감상하는 것보다 자료를 빨리 찾고 입력해야 합니다.

따라서 구현 방향은 다음과 같습니다.

| 화면 | 디자인 적용 방법 |
|---|---|
| 프로젝트 목록 | 큰 제목·도해·요약 수치로 전체 분위기 표현 |
| 프로젝트 내부 | 프로젝트명과 탭을 안정적으로 유지 |
| 목록·표 | 정렬·검색·상태 파악을 우선 |
| 상세 | 파일·이미지·사양·기록을 충분히 읽을 수 있게 구성 |
| 등록·수정 | 명확한 레이블, 오류 위치, 저장 상태 표시 |
| 모바일 | 한 열 중심 배치, 필요한 표·탭만 부분 가로 스크롤 |

스크롤·커서 모션은 장식 요소이며 버튼 클릭이나 입력을 방해하면 안 됩니다. 모션 감소 설정에서는 해당 연출을 줄이거나 꺼야 합니다.

한국어/영어 전환은 메뉴·버튼·안내문에 적용하고 사용자 입력을 자동 번역하지 않습니다. 날짜·숫자 표시는 언어에 맞게 바꾸되 저장 데이터는 같은 값을 유지합니다.

PNG 로고 교체는 원본 비율을 유지하고, 잘못된 파일·용량 초과·읽기 실패를 구분해 안내해야 합니다.

---

**9. 실제 개발은 이 순서가 적절합니다.**

| 단계 | 작업 | 완료 판단 기준 |
|---|---|---|
| 1. 정책 확정 | 초대·배정·확정·업체 설정 담당자 결정 | 누가 어떤 행동을 할 수 있는지 표로 설명 가능 |
| 2. 서버 기반 | 인증, 업체, 소속, 프로젝트, 배정 | 다른 업체·미배정 프로젝트 접근 거절 |
| 3. 프로젝트 기본 | 목록, 생성, 수정, 개요, 전환 | 직접 링크·새로고침·뒤로가기 정상 |
| 4. 업무 데이터 | 6개 탭과 상세·폼 | 저장한 내용이 목록·상세·요약에 일관되게 반영 |
| 5. 파일 처리 | 업로드 검증, 비공개 저장, 다운로드, 비교 | 접근권한 없는 파일 및 잘못된 형식 거절 |
| 6. 역할별 연결 | 고객 화면, 시공팀 배정·업로드 | 역할·배정·기간에 따라 동작 분리 |
| 7. 공통 기능 | 변경이력, 알림, 고객 관리 | 정규 상세로 연결되고 권한 재검사 |
| 8. 운영 검증 | 모바일, 접근성, 실패 복구, 백업 | 실제 사용·오류 상황에서 데이터와 권한 유지 |

디자인 작업과 화면 개발은 병행할 수 있지만, **권한 정책이 필요한 기능을 정책 없이 먼저 활성화하는 순서**는 피해야 합니다.

---

**10. 완료 여부는 무엇으로 검증해야 하는가**

화면이 정상적으로 보이는 것과 서비스가 올바르게 동작하는 것은 구분해야 합니다.

| 검증 영역 | 확인할 사례 |
|---|---|
| 업체 격리 | 업체 A 사용자가 업체 B의 ID를 직접 넣어도 접근 불가 |
| 배정 | 미배정·만료·회수된 계정의 조회·업로드 거절 |
| 공개 상태 | 비공개 항목이 고객 목록·검색·알림·다운로드에 노출되지 않음 |
| 요청 기록 | 정정 후에도 원문이 유지됨 |
| 견적 버전 | 새 버전 등록 후 이전 파일과 설명이 유지됨 |
| 이미지 비교 | 0·50·100%, 서로 다른 비율, 읽기 실패, 키보드·터치 |
| 저장 실패 | 실패를 성공으로 표시하지 않고 입력을 복구할 수 있음 |
| 동시 수정 | 다른 사람의 수정 내용을 조용히 덮어쓰지 않음 |
| 탐색 | 직접 링크·새로고침·뒤로가기에서 같은 항목 유지 |
| 모바일 | 주요 작업을 가로 넘침·가려진 버튼 없이 수행 |
| 변경이력 | 변경자·서버 시각·전후 값이 실제 변경과 일치 |
| 복구 | 데이터와 파일을 함께 복원할 수 있음 |

이 검증을 통과해야 운영 가능한 서비스라고 판단할 수 있습니다.

---

**11. 현재 결과물과 남은 작업을 구분하면**

현재 구현한 것은 **디자인과 업무 흐름을 검토할 수 있는 로컬 프런트엔드**입니다.

프로젝트와 6개 업무 탭, 고객 연락처, 변경 전후 이력, 고객 홈 편집, 비교 이미지, 견적 버전 추가, 한국어/영어, PNG 로고 변경 등을 브라우저 저장 방식으로 구현했습니다.

반면 다음은 아직 운영 기능으로 연결되지 않았습니다.

- 실제 로그인과 계정 관리
- 업체별 데이터 격리
- 프로젝트 초대·배정·만료·회수
- 시공팀의 실제 배정 현장 조회와 업로드
- 서버 파일 검증과 비공개 다운로드
- 실제 알림 생성·발송
- 서버 변경이력과 백업·복구
- 고객 확정자 정책에 따른 확정 처리

또한 현재 사진 필터·자재 검색·일정 표현 등은 검토판 수준입니다. 운영판에서는 파일별 업로드 상태, 동시 수정, 날짜·공간의 세부 필터, 실제 계정 기반 업로더 정보까지 보완해야 합니다.

**12. 다음 단계 전에 결정해야 할 질문**

| 결정 사항 | 정해야 하는 내용 |
|---|---|
| 프로젝트 배정 | PM은 업체의 모든 프로젝트를 보나, 배정된 것만 보나? |
| 초대·배정 수행자 | 어떤 PM이 고객과 시공팀을 초대·배정할 수 있나? |
| 고객 확정 | 프로젝트별 확정자는 한 명인가, 여러 명인가? |
| 확정 후 변경 | 사양이나 도안이 바뀌면 재확정이 필요한가? |
| 시공팀 권한 | 사진 조회 범위와 수정·삭제 가능 범위는 어디까지인가? |
| 견적 공개 | 이전 공개 버전을 고객이 계속 볼 수 있나? |
| 자료 삭제 | 삭제 대신 보관 처리할 항목과 보존 기간은 무엇인가? |
| 초기 업체 등록 | 누가 최초 업체와 담당자를 등록하나? |
| 로그인 방식 | 초대 이메일 기반인지, 비밀번호 방식인지? |
| 운영 환경 | 도메인, 서버 지역, 예상 사용자·파일 규모는 어느 정도인가? |

이 중 앞의 권한 관련 항목을 먼저 확정하면, **현재 화면 구조를 유지하면서 서버와 실제 업무 동작을 연결하는 단계**로 넘어갈 수 있습니다.
