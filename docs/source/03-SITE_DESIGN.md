## 0. 문서 개요

### 0.1 목적과 범위

본 문서는 「① 아이디어 가이드 문서」에서 정의한 멀티테넌트 SaaS 방향을 실제 화면·데이터·기능 단위로 구체화한 사이트 설계문서다. 정보구조(IA), 역할·권한, 화면별 상세 명세, 데이터 모델, 비기능 요구사항, 릴리즈 계획을 다루며, 특정 프로그래밍 언어나 라이브러리에 종속되지 않는 "무엇을 만들 것인가"에 집중한다. 기술 스택·코드 구조·개발 프롬프트는 「③ 아키텍처 문서」에서 이어받는다.

### 0.2 용어 정의

| 용어 | 정의 |
| --- | --- |
| 업체 (Company / Tenant) | 본 플랫폼을 구독해 사용하는 인테리어·리모델링 시공사 한 곳. 데이터는 업체 단위로 완전히 격리된다. |
| 플랫폼 운영자 (Platform Admin) | 이 SaaS 서비스 자체를 운영하는 주체. 모든 업체를 총괄한다. |
| 업체 총관리자 (Company Admin) | 한 업체 내부의 최고 관리자. 원본 기획안의 "총관리자"에 해당. |
| 프로젝트 관리자 (PM) | 담당 프로젝트를 생성·운영하는 업체 소속 직원. |
| 고객 (Customer) | 인테리어 시공을 의뢰한 최종 고객. 프로젝트 단위로 초대되어 고객 포털을 이용한다. |
| 프로젝트 (Project) | 고객 1명과 연결된 하나의 시공 건. 모든 콘텐츠(디자인·자재·사진·일정 등)의 귀속 단위. |
| 블록 (Block) | 자유 배치형 CMS 편집기를 구성하는 최소 콘텐츠 단위(텍스트, 이미지, 자재 카드 등). |
| 공개 상태 (Visibility) | 콘텐츠가 고객에게 보이는지 여부와 시점(초안 / 검토 / 예약 / 공개). |
| 프로젝트 확정 코드 | 프로젝트마다 하나씩 발급되는 코드. 프로젝트 관리자가 개인 경로로 결정권자에게 전달하며, 입력한 계정만 승인·확정 지시를 할 수 있다. 재발급하면 기존 확정 상태가 무효가 된다. |
| 프로젝트 접근 | 고객 계정이 특정 프로젝트를 열람할 수 있는 권한. 프로젝트 관리자의 초대로 부여되며 한 프로젝트에 여러 계정을 둘 수 있다. |
| 멤버십 (Membership) | 계정이 특정 업체에서 갖는 역할(업체 총관리자 / 프로젝트 관리자). 한 계정이 여러 업체에 서로 다른 역할로 속할 수 있다. |

| --- | --- |

| ③ 아키텍처 문서 | 본 문서의 하위 구체화 — 기술 스택·시스템 구조·데이터 스키마·보안 설계 |

## 1. 서비스 개요와 설계 원칙

본 서비스는 인테리어 업체가 고객별 프로젝트를 생성하고 디자인, 자재, 요청사항, 현장 진행 사진, 일정 및 변경 기록을 하나의 웹 환경에서 운영하도록 설계한다. 고객용 프로젝트 페이지는 프로젝트 관리자가 직접 구성하며, 업체 총관리자는 업체 내 권한·템플릿·운영 기준을 관리하고, 플랫폼 운영자는 전체 업체(테넌트)와 구독·정책을 관리한다.

파일 전달과 메신저 중심의 단절된 업무 방식을 프로젝트 단위의 기록형 업무 흐름으로 전환한다. 모든 콘텐츠와 활동은 프로젝트에 귀속되며, 역할 기반 권한, 공개 상태, 버전 및 감사 기록을 기준으로 운영한다.

### 1.1 설계 원칙

테넌트 격리 우선: 모든 데이터·조회·파일 접근은 업체(company_id) 경계를 벗어날 수 없다. (9장 참고)

역할 기반 접근 제어: 4단계 역할(플랫폼 운영자/업체 총관리자/프로젝트 관리자/고객)에 따라 화면과 기능이 달라진다.

공개 상태의 명시적 관리: 모든 고객 노출 콘텐츠는 초안 → 검토 → (예약) → 공개 상태를 가지며 실수 공개를 구조적으로 방지한다.

버전과 이력의 보존: 디자인·자재·댓글은 이전 상태를 삭제하지 않고 버전/이력으로 남긴다.

기록 가능한 신뢰: 주요 행위는 AuditLog에 남아 사후에 "누가, 언제, 무엇을" 했는지 재구성할 수 있다.

## 2. 사용자 역할과 권한 체계

### 2.1 역할 정의

| 역할 | 소속 범위 | 운영 책임 | 주요 권한 |
| --- | --- | --- | --- |
| 플랫폼 운영자 | 전체 서비스 (company_id 없음) | 서비스 및 전체 업체 운영 | 업체 생성·정지, 요금제·결제·구독 관리, 플랫폼 공통 템플릿, 시스템 정책, 전체 AuditLog |
| 업체 총관리자 | 업체 1곳 | 업체 서비스·조직 운영 | 업체 내 멤버 초대와 권한 부여·회수, 전체 고객·프로젝트, 업체 템플릿 승인, 저장공간, 알림 정책, 업체 AuditLog. 본인에게 프로젝트 관리자 권한을 함께 두어 실무를 직접 수행할 수 있다 |
| 프로젝트 관리자 | 업체 내 담당 프로젝트 | 담당 프로젝트 생성·운영 | 고객 등록, 프로젝트 생성, 페이지 편집, 콘텐츠 업로드·공개, 댓글 삭제, 일정·디자인·자재·사진 관리 |
| 고객 | 초대받은 프로젝트 | 본인 프로젝트 확인·의견 전달 | 회원가입 후 초대받은 프로젝트 열람, 요청·댓글 작성, 본인 댓글 수정, 확정 코드 입력 시 디자인·자재 승인 및 확정 지시 |

## 3. 정보구조(IA)와 사이트맵

사이트는 접근 주체에 따라 5개 영역으로 나뉜다. URL 구조는 예시이며 「③ 아키텍처 문서」의 라우팅·폴더 구조와 그대로 대응한다.

| 경로(예시) | 화면 | 설명 |
| --- | --- | --- |
| / | 랜딩 페이지 | 가치제안, 핵심 기능 소개, 고객 사례, CTA(무료로 시작하기) |

E. 고객 영역 (/portal/*)

고객은 회원가입 후 초대를 수락한 프로젝트만 열람할 수 있다. 로그인 한 번으로 서로 다른 업체의 프로젝트까지 한 목록에서 확인하며, 업체 브랜딩(로고·색상)이 적용된 화면으로 제공된다. 댓글은 접근 권한만 있으면 쓸 수 있고, 디자인·자재 승인과 확정 지시는 프로젝트 확정 코드를 입력한 뒤에만 가능하다. 상세 규칙은 4.7절에서 다룬다.

## 4. 화면별 상세 설계

### 4.1 회원가입 · 업체 개설 플로우

계정 가입과 업체 개설을 분리한다. 누구나 계정을 만들 수 있고, 업체를 개설한 계정이 그 업체의 총관리자가 된다.

1단계 — 회원가입: 이름·이메일·비밀번호 입력, 약관 동의와 개인정보 국외 이전 동의를 각각 받는다

2단계 — 이메일 인증: 인증 메일의 링크를 열어 계정을 활성화한다

3단계 — 업체 개설: 업체명·사업자 형태를 입력하면 업체가 만들어지고, 개설한 계정에 총관리자와 프로젝트 관리자 권한이 함께 부여된다

4단계 — 업체 상태는 곧바로 정상(active)이며 전 기능을 제한 없이 사용한다 (요금제 미적용)

5단계(선택) — 온보딩 체크리스트: 첫 고객 등록, 첫 프로젝트 생성, 첫 고객 초대

### 4.2 프로젝트 관리자 워크스페이스 — 자유 배치형 CMS 편집기

프로젝트 관리자는 고객이 보는 프로젝트 홈을 블록 단위로 조합한다. 블록은 드래그 배치, 크기 조정, 복제, 숨김, 공개 예약이 가능하며 완성한 구성을 프로젝트 템플릿으로 저장하거나 업체 공통 템플릿 승격을 제안할 수 있다. 디자인·자재·사진·일정·요청 화면은 고정 양식을 유지하며, 자유 배치는 홈 한 장에만 적용한다.

| 편집 블록 | 주요 활용 | 공개 상태 관리 |
| --- | --- | --- |
| 텍스트·제목 | 설명, 안내, 공사 단계, 강조 메시지 | 초안/공개 |
| 이미지·갤러리 | 도면, 현장사진, 시공 전후 이미지 | 초안/공개, 개별 이미지 단위 숨김 가능 |
| Before & After | 같은 위치의 이전·이후 이미지 비교 | 두 이미지 모두 공개되어야 노출 |
| 디자인 파일 | PDF·이미지 미리보기와 버전 연결 | DesignVersion의 공개 상태를 따름 |
| 자재 카드 | 자재 사양·이미지·외부 자료 링크 표시 | 자재 항목의 공개 여부를 따름 |
| 일정·캘린더 | 마일스톤, 방문 및 공정 일정 | 일정 단위 공개 가능 |
| 댓글·요청사항 | 고객 질의와 답변을 시간순으로 표시 | 삭제된 댓글은 비노출, 이력은 보존 |
| 진행 공정 | 공정별 사진과 상태를 묶어 표시 | 공정 단위 공개 |
| 버튼·링크 | 파일 보기, 확인·승인, 외부 링크 이동 | 항상 공개(콘텐츠 자체가 비공개면 비활성) |
| 구분·여백 | 페이지 흐름과 시각적 계층 구성 | 해당 없음 |

> 💡 편집기의 상태값(공개 상태, 블록 순서/위치, 예약 시각)은 8장 Page·Block 엔터티에 그대로 매핑된다.

### 4.3 디자인 버전 관리 (/designs)

디자인은 버전 단위로 관리한다. 버전명, 파일, 미리보기, 변경 설명, 등록자, 등록 시각, 공개·승인 상태를 저장하고 새 버전을 공개하면 고객 화면의 최신 디자인을 자동 갱신한다. 이전 버전은 보존하여 변경 근거와 승인 이력을 확인한다.

### 4.4 자재 조회와 구매 진행 (/materials)

자재는 제품명, 브랜드, 규격·색상, 적용 위치, 이미지, 설명, 외부 URL 또는 첨부 자료를 관리한다. 고객 공개 여부와 확인·승인 상태를 구분하고, 자재별 견적 → 주문 → 배송 → 설치 → 완료 흐름을 관리해 구매 및 설치 현황을 함께 추적한다.

| 구매 진행 단계 | 설명 |
| --- | --- |
| 견적 | 자재 확정 전, 가격/사양 검토 중 |
| 주문 | 고객 확인 후 발주 완료 |
| 배송 | 제조사/판매처에서 배송 중 |
| 설치 | 현장 설치 진행 중 |
| 완료 | 설치 완료 및 최종 확인 |

### 4.5 요청사항 메모와 댓글 이력 (/requests)

댓글에는 작성자와 작성 일시를 표시한다. 프로젝트에 접근 권한이 있는 고객은 일반 댓글을 쓸 수 있고, 본인 댓글만 수정할 수 있다. 수정 전후 내용과 시각은 이력으로 남는다. 구속력이 있는 확정 지시는 확정 코드를 입력한 계정만 남길 수 있으며 별도 배지로 구분되고 수정·삭제할 수 없다. 일반 댓글의 삭제 권한은 프로젝트 관리자와 업체 총관리자에게만 부여한다.

### 4.6 플랫폼 운영자 콘솔 상세

업체 상태 관리: 활성(Active) → 연체(Past due) → 정지(Suspended) 상태 전이를 지원한다. 체험(Trial) 상태는 두지 않으며 가입 즉시 활성이다. 정지 시 해당 업체의 로그인만 차단하고 데이터는 보존한다.

결제 실패 대응(유료화 이후): 결제 실패 업체 목록을 우선 노출하고, 유예 기간(기본 3영업일) 경과 시 자동 정지 처리한다.

전체 감사로그: 업체별 감사로그를 넘나드는 조회는 플랫폼 운영자만 가능하며, 이 조회 행위 자체도 로그로 남긴다.

### 4.7 고객 접근과 확정 코드

고객 화면은 두 단계로 권한을 나눈다. 첫 단계는 열람과 대화다. 고객이 회원가입한 뒤 프로젝트 관리자가 보낸 초대를 수락하면 그 프로젝트의 공개된 콘텐츠를 보고 일반 댓글을 쓸 수 있다. 한 프로젝트에 배우자·가족 등 여러 계정을 초대할 수 있고, 프로젝트 관리자는 참여자 목록에서 접근을 언제든 회수할 수 있다.

고객 초대 링크는 초대장의 이메일에 묶지 않는다. 집주인이 배우자·가족에게 링크를 그대로 전달하는 것이 정상 사용이기 때문이다. 대신 누군가 수락하면 초대한 프로젝트 관리자에게 알리고, 감사 기록에 초대자와 수락자를 함께 남긴다. 반면 **업체 구성원 초대는 초대장의 이메일과 수락 계정의 이메일이 같아야만 수락된다.** 스태프 권한은 링크 하나가 새는 것으로 넘어가서는 안 되기 때문이다.

고객이 보는 화면은 본인이 초대받은 프로젝트 안으로만 한정된다. 같은 업체의 다른 프로젝트는 주소를 직접 입력하든 내부 식별자를 넣든 열리지 않는다.

두 번째 단계는 확정이다. 디자인·자재 승인과 확정 지시처럼 책임 소재가 걸리는 행위는 프로젝트마다 하나씩 발급되는 확정 코드를 입력한 계정만 할 수 있다. 코드는 프로젝트 관리자가 화면에서 발급해 카카오톡·문자 등 개인 경로로 결정권자에게 전달하며, 시스템에는 해시로만 저장되어 발급 직후 화면에서 한 번만 볼 수 있다. 로그인만으로는 '이 집의 결정권자'임을 보장할 수 없기 때문에 이 단계를 따로 둔다.

확정 코드 검증은 프로젝트와 계정 기준으로 시도 횟수를 제한하고, 발급·성공·실패를 모두 감사 로그에 남긴다. 유출이 의심되면 프로젝트 관리자가 재발급하며, 재발급 시 기존에 확정 권한을 얻은 계정은 모두 무효가 되어 새 코드를 다시 입력해야 한다. 업체 총관리자와 프로젝트 관리자는 확정 코드 없이 업체 내부 작업(콘텐츠 편집·공개, 고객 초대, 확정 코드 발급 등)을 수행한다. 디자인·자재 승인·반려와 확정 지시 댓글은 고객이 확정 코드를 입력한 뒤에만 가능하며, 스태프가 대신 승인 상태를 바꿀 수 없다.

## 8. 핵심 데이터 모델

관계형 데이터베이스를 기본으로 하고 파일은 별도 객체 스토리지에 보관한다. 모든 테이블은 생성·수정 시각, 작성자, 공개 상태를 공통 필드로 가지며, company_id 필드를 통해 멀티테넌트 데이터를 격리한다 (플랫폼 전역 엔터티인 Company·PlatformAdmin 제외).

### 8.1 엔터티 관계 개요

User(계정)는 업체에 직접 속하지 않는다. Membership(user, company, role)으로 업체별 역할을 갖는다

ProjectVerification(project, user, codeVersion) — 확정 코드를 입력해 확정 권한을 얻은 계정

ProjectAccess(project, user) — 고객 계정의 프로젝트 열람 권한. 한 프로젝트에 여러 계정 가능

Company 1 : 1 Subscription, Subscription 1 : N Invoice — 요금제·결제 이력

Customer 1 : N Project — 고객은 여러 프로젝트를 가질 수 있음

Project 1 : N (Page·Block, DesignVersion, Material, Comment, ProgressPhoto, Schedule) — 모든 콘텐츠는 프로젝트에 귀속

플랫폼 운영자는 users.is_platform_admin=true이며 업체 멤버십이 없다. 전 테넌트 접근이 가능한 유일한 예외다

Template — scope=platform(전 업체 공통, company_id 없음) / scope=company(업체 공통) / scope=project(프로젝트 전용)의 3단계로 관리

고객 화면 접근은 ProjectAccess가 관리한다. 한 계정은 여러 업체의 프로젝트에 초대될 수 있다. Customer는 업체의 연락처 레코드이며 로그인 계정과 1:1로 묶이지 않는다
